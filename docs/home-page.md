# Home page

The Home tab shows one project on one page: a top bar, the active view in the centre, an inspector on
the right and a strip at the bottom. One selected place ("where": a group, area or part of the
project's map) is kept across every view and in the address, so a link opens the same view and place.

```
/dashboard/home/<view>?where=<box id>&hproject=<project slug>
```

Views, in order, with their number keys: Overview (1), Map (2), Lanes (3), Tickets (4), How it runs (5).
Arrows move inside the view switch and the inspector tabs.

- **Overview (1)**: one sentence ("In Mixer: 1 thing needs you. 3 running, 2 ready.") and cards: Needs you,
  Running now, On the agenda, Finished lately, Open notes, Where the work is, Health. Every row opens its ticket.
- **Map (2)**: the project drawn as boxes, from groups down to an area's parts, with live counts and dots.
- **Lanes (3)**: the Plan page's For you, Ready, Auto queue and lanes, narrowed to the selected place. Ticking a
  check, the Auto switch and Alt+arrow moves in the Auto queue save exactly as on the Plan tab (same code).
- **Tickets (4)**: one table of every ticket (below).
- **How it runs (5)**: the life of a note as a flow, then every automation and service with its state.

The **inspector** on the right has tabs: Notes (open notes of the place, `N` writes one), Work (the place's
epics), Tickets (its open tickets by state) and How it works (the place's handbook page). The **top bar** holds
the project switcher, the selected place (its name; the parent too when there is room; `×` clears it), the
view switch, search (`⌘K`), Note (`N`) and the usage chip (this week's cost; click for the details). The
**strip** at the bottom says what is for you, any health problem (click: How it runs, problems only) and what
is running (click: the running panel). Under 1500 px wide the usage chip drops its reset time, under 1200 px
the search button shows only its icon; nothing clips.

### Which tickets a project shows

One rule, `shared/home-scope.js`, for every view, tab, strip item, `GET /api/home/running` and
`ch tasks running --project`: an epic is the project's when its project is the Home project or one of its
sub-projects, or when an area of the map claims it by lane or `projects` (or by a `match` word, only when the
group lists `keywordProjects`). A ticket is in when its epic is, or, with no epic, when its own project is.
A selected place narrows that further to the place's epics. Free notes follow their own `project`.
"Running" always means live work (working, waiting on CI, waiting on you); idle work is listed but not
counted, so the Overview card, the strip, the Map dots, the Tickets "Running" chip and the CLI agree.
The Map (2) lays itself out for the window at every level (it does not use `box`): click or `Enter` zooms into a box, `Esc`/`Backspace` zooms out, `Home` goes to the top; an area's epics on none of its parts show in a dashed "Whole area" box, and the inspector's Work tab lists the selected place's epics (code: `dashboard/js/home-map*.js`, numbers: `shared/home-map-stats.js`).

The palette (`Mod+K`, or the button "Search or jump…" in the top bar) lists, in groups with a hint on the
right of each row: **Places** (every group, area and part of the map with its path; Enter selects it and
keeps the current view, `Mod+Enter` selects it and opens the Map), **Tickets** (by id or title, with the
ticket's section; Enter opens it), **Views** (the five views and the inspector tabs) and **Commands**. With
nothing typed it shows the places and tickets you picked last (remembered per project in this browser) and
the commands. Several words must all match; letters may be spread over a word (`tmln` finds Timeline), an
exact ticket id always comes first, and at most 50 rows are drawn.

Built-in commands: Add a note (sends a `hm:note` event on `document` for the note box), Clear the selected
place, Switch project to ..., Toggle theme (the header's theme button), Copy link to this view, Open keyboard
help, Open usage (the top bar chip), Show how it works for this place (the inspector tab). Open tickets rank above done and archived ones at equal match quality. A view that has a search box of its own keeps `/` by setting `data-hm-claims-slash` on its root element.
Any feature adds its own with `registerHomeCommand`, see below.

## Pointing a project at its config

Each project describes itself in its own `home.config.json`. The tracker's `config.json` says where
each one lives, by project slug (absolute paths only, `.json` files only):

```json
"home": { "bakery": "/Users/you/code/bakery/home.config.json" }
```

### Use it for another project in five steps

1. Copy [`home.config.example.json`](../home.config.example.json) (a made-up bakery) into the project's
   repo as `home.config.json`.
2. Set `title` and `repos` (folders relative to the file), then draw `groups` > `areas` > `parts` with the
   `lanes` each place owns; add `match` words only for titles the lanes miss.
3. Point the tracker at it: `"home": { "bakery": "/abs/path/home.config.json" }` in the tracker's `config.json`.
4. Open `/dashboard/home/map?hproject=bakery`: problems in the file are listed above the view; epics no area
   claims sit in the `fallback` area (`unmatchedEpics`), give them a lane or a place.
5. Add `automations` and `services` with a `status` reader each, and a `page` per box for How it works.
   Each project keeps its own view, place and ticket filters.

A project without an entry shows a "Set up this project" card. Start from
[`home.config.example.json`](../home.config.example.json) (a made-up bakery). Problems in the file
are listed above the view in plain words (which key, what is wrong); the rest of the file is still used.

## Schema (version 1)

Keys starting with `$` (like `$comment`) are ignored. Any other unknown key is reported.

- **`version`**: `1`. A newer number is refused with a message; leaving it out means 1.
- **`title`**: the project's name as Home shows it.
- **`repos`**: the project's repositories, for the views that show where code lives and for finding live
  work (worktrees, recent branches, pull requests). Each entry is a path (`"bakery-site"`) or an object
  `{ "name": "Orders", "path": "bakery-orders" }`. Paths are relative to the folder of this file (absolute
  paths work too); `name` defaults to the folder's name. In the older flat shape a text entry is relative to
  the git top-level folder at or above the file instead, so a config kept in `docs/` can say `"."` for the
  repo itself. A path that is not an existing folder is left out and reported as a warning.
- **`fallback`**: the id of the area that takes epics no area claims (see "Where an epic belongs"); the last
  area when left out.
- **`groups`**: the top level of the map, e.g. "Shop floor" and "Kitchen". Each group has an `id`, a
  `name` and its `areas`, and may have `box`, `page`, `covers` and `keywordProjects` (the projects
  whose ticket titles may be matched by its areas' `match` patterns; `null` in the list means tickets
  with no project).
- **`areas`** (inside a group): the places work belongs to. An area has:
  - `id`: letters, digits, `-` and `_`; unique across every group, area and part (it goes in the address).
  - `name`: what the page shows.
  - `what`: optional one line saying what the place is (groups and parts have it too).
  - `lanes`: tracker lanes whose tickets belong here.
  - `match`: a pattern (regular expression, any case) tested against ticket titles.
  - `projects`: tracker projects whose tickets belong here.
  - `box`: `[x, y, width, height]` of the area on the map drawing.
  - `page`: the handbook page of the area: a `.md` path relative to the config file (see "Handbook pages").
  - `covers`: what the area covers; used for staleness when its page has no `covers` of its own.
  - `parts`: smaller places inside the area, same keys as an area (one level only).
- **`cables`**: lines on the map between two places: `from` and `to` are ids, `path` is an optional
  SVG path, `label` an optional caption.
- **`pages`**: optional `{ "<box id>": "<page path>" }`, to give boxes pages without touching their entries (a `page` on the box wins; works for the older flat shape too). **`page`** at the top is the project's own page, shown when nothing is selected.
- **`decorations`**: optional path of an SVG file drawn behind the map, relative to the config file.
- **`services`**: the outside services the project depends on: `id`, `name` and `what` (one line), plus
  the keys under "How it runs" below. Keys this page does not know are kept for later features.
- **`automations`**: jobs that run by themselves (schedules, hooks, CI, runs inside another job): `id`,
  `name`, `what`, plus the keys under "How it runs" below. Unknown keys are kept, as for services.
- **`lifecycle`**: optional changes to the "How it runs" flow (below).

### How it runs: automations, services and the flow

The "How it runs" view (key 5) draws the life of a note as a flow (note written, filed and explained,
ready, being built, questions for you, waiting for your checks, done) with live counts, then lists every
automation and service with its state. `ch tasks automations [--project <slug>] [--json]` prints the same
list in the terminal. The lower strip shows "2 automations late" only while something needs a look.

An **automation**:

| Key | What it is |
| --- | --- |
| `trigger` | when it runs, in words ("every 10 min", "before every commit") |
| `kind` | `launchd`, `cron`, `hook`, `ci`, `skill`, `file` or `inside` (runs inside another job) |
| `group` | the heading it is listed under; by default from `kind`: Scheduled jobs, Inside another job, Hooks, CI, By hand |
| `status` | where its last run can be read: one source or a list of sources (below); left out = no status |
| `docs` | a web address or file path about it |
| `run` | editable LaunchAgent settings: `schedule`, `harness`, `model`, `effort`, `cli`, `arguments`, `runner`, `skill`, `prompt` and `enabled` |
| `automationDefaults` | project-wide `harness`, `model`, `effort`, `cli`, `arguments`, `runner`, `skill` and `prompt` defaults for jobs without an override |

The `harness` is `opencode`, `claude`, `codex`, `copilot`, or `custom`, and must be explicitly configured along with `cli`.
The installer never chooses a provider silently. The selected harness controls the non-interactive
command shape; `cli` may be a command on `PATH` or an absolute path, and `arguments` appends additional argv values before the
prompt. `model` and `effort` remain optional because each harness supports a different set of model controls; `effort`
is not injected as a flag unless the selected CLI documents one, in which case add it through `arguments`.

Click **Edit** on an automation row to change its description and, for a `launchd` automation, its local schedule,
harness, model, effort, CLI executable, extra arguments, runner path, skill, optional full prompt and enabled switch. Click **Defaults** above
the list to change inherited values for the whole project. The editor has a shareable address:
`/dashboard/home/how-it-runs/edit/<automation-id>?hproject=<project>`. Cancel, Close and browser Back return to the
table without writing; Save validates the whole change, updates the mapped `home.config.json` atomically and
reloads only that LaunchAgent. `/dashboard/automations` is a short link to the same table.

A **service**: `usedBy` (the group, area or part ids that use it), `console` (the https address of its
console, shown as an Open console button), `status` (one source or a list) and `cost` (text, or
`{ "note": "..." }`).

A **status source** is `{ "type": ..., ... }`. Paths may start with `~`; a relative path is read from the
config file's folder. Every reader only reads, gives up after a few seconds, and says in plain words why
it cannot tell (the chip is then "unknown").

| `type` | Needs | Reads |
| --- | --- | --- |
| `mtime` | `path`; `match` (a folder's entries to count, by name pattern, e.g. `^\\.git$`) | the newest change of a file or folder; with `match`, only the matching entries (so other writers to the folder do not hide a stopped job) |
| `json-file` | `path`; `field` (a time, default `at`, dots for nested keys), `okField` | a time and an ok/failed field of a JSON file |
| `log-tail` | `path`; `okPattern`, `failPattern` | the last non-empty line of a log and the time it starts with (else the file's time) |
| `launchctl` | `label` | `launchctl print gui/<uid>/<label>`: loaded or not, last exit code, run interval or calendar times (the next run). The dashboard server must run outside a sandbox for this. |
| `gh-workflow` | `repo` (`owner/name`), `workflow` (its name) | the last run through the `gh` command, cached for a minute |
| `http` (services) | `url` | a GET with a 3 s timeout. Only `https://`, or `http://` to localhost; never an address with a user, password, `token`, `key=` or `secret` in it. The tracker never sends credentials: a service that needs a sign-in uses `none` and its console link. |
| `none` | | nothing; the row shows what it is and its console link |

Any source can add `maxAgeMin`: a last run older than that many minutes makes the chip "late". Services
take `gh-workflow`, `http`, `json-file` or `none`. The chip is **ok** (ran, nothing failed), **late**,
**failed** (a failed exit, a fail pattern, a red CI run, a service that does not answer), **off**
(launchd does not know the job) or **unknown**. With several sources, a failure wins and the newest run
counts.

`lifecycle` relabels or hides steps of the flow: `{ "stages": [{ "id": "ready", "label": "Queued" },
{ "id": "filed", "hide": true }] }`. Step ids: `note`, `filed`, `ready`, `running`, `asks`, `review`, `done`.
A stage can also name what does its work: `job` (an automation id: the open step shows "Done by: <name>"
and a click scrolls to that row and opens its fold), `skill` (the skill file, shown as text) and `page` (a
handbook page path: "Open its page"). Hover a line to read what travels on it; a dotted "waits on" line runs
from the question step back to the running sessions that wait for you, and its label opens exactly those
sessions. `lifecycle.ai` draws the small second map, "where an AI answer comes from":
`{ "title": "...", "nodes": [{ "id", "name", "what", "box?" }], "edges": [{ "from", "to", "label?" }] }`; a node
with a `box` (a group, area or part id) opens that place's handbook page. Keep every `what` to one line
(a glance view; the suite's handbook check allows 90 characters) and put the depth in the handbook page.

Server: `GET /api/home/automations?project=<slug>` and `GET /api/home/services?project=<slug>` answer each
entry with its `result` (`{ lastRun, ok, late, nextRun?, detail, off?, sources }`); results are cached for
60 s and the readers run in parallel, so a slow one answers `{ checking: true }` and fills in on the next
request. `PUT /api/home/automation?project=<slug>` accepts `{ id, description?, schedule?, model?, skill?,
prompt?, enabled? }`, validates it and saves one automation. Runtime changes invoke the local LaunchAgent
installer without a shell; a reload failure rolls the config file back.

### The older flat shape

A file without `version` whose `groups` is an object (`{ "<id>": "<name>" }`) is read as the older
flat shape: a top-level `areas` list where each area names its `group`, and `keywordProjects` as an
object of group id to project list. It is turned into version 1 on load (areas nested under their
group), so such a file needs no change.

### Where an epic belongs

`shared/home-areas.js` puts every epic in one area (and in one of its parts, when a part claims it). The
first rule that fits wins: (1) an area whose `lanes` hold the epic's lane; (2) an area whose `match` fits the
epic's title, only when the epic's project is in the area's group `keywordProjects` (a group without the key
allows every project, but then only the Home project's own epics count as on its map); (3) an area whose `projects` hold the epic's project; (4) the `fallback` area. Areas
are tried in the order of the file (groups first to last, areas first to last). Epics that reach rule 4 are
listed by `unmatchedEpics`, so the map's owner can give them a place.

## Handbook pages

A box (group, area or part) can have a page that explains how that part really works: the
inspector's "How it works" tab shows it, with its diagrams. A box without a page shows its nearest
parent's page ("showing Kitchen's page"); with none up the tree it says "No page yet" and names the file
to create. Pages are plain files in the project's own repo, so agents read the same text.

```
---
title: "Counter and till: how a sale is rung up"
updated: 2026-11-03
covers: [bakery-orders/till/**, bakery-orders/receipts.js]
---

## What it is
...
![A sale from basket to receipt](img/counter-sale.svg)
```

- **Front matter**: `title` (quote it if it holds a colon), `updated` (`YYYY-MM-DD`, the day every claim was last checked against the code) and `covers`, an inline list `[a, b]` (or `- item` lines) of
  `<repo name>/<glob>`. A missing field is a note on the page, never an error.
- **Body**: headings, paragraphs, bullet and numbered lists (wrapped lines are fine), tables, fenced code, bold,
  italic, `code`, links and images. Raw HTML is shown as text, never run. A link to another page of the
  project (`other.md`) selects that page's box; `http(s)` links open in a new tab.
- **Diagrams** are plain `.svg` files next to the page (`img/<box id>-<topic>.svg`), drawn by hand, no diagram
  library, no script, no outside links. They carry their own background, are shown through `<img>` only
  (never inlined) and open large on a click. `.png`, `.jpg` and `.webp` work too.
- **Where files may live**: anywhere inside the folder that holds `home.config.json`; the server refuses
  `..`, absolute paths, hidden files, links that lead outside and any other file type. A page is `.md`;
  an image is `.svg`, `.png`, `.jpg` or `.webp`. A sample project is in `cli/test/fixtures/home-pages/`.
- **Staleness**: when commits touched a `covers` glob after the end of the `updated` day, the page says
  "may be out of date: 14 commits since 3 Nov" with the list (newest 30, merge commits ignored, checked at most
  every 10 minutes). The repo name in a `covers` entry is one of `repos` in the config (an entry is a name or
  path, or `{ "name": "...", "path": "..." }` with a path relative to the config file or absolute). A repo that
  is not on disk is a note, not an error. After checking a page against the code, set `updated` to today.
- **List them**: `ch tasks pages [--project <slug>] [--stale] [--json]` shows every box as has a page / stale
  (n commits) / missing (page set, file absent) / no page set.
- **Read it on a phone**: a page is only a file; ask a Claude session to "publish `<page path>` as a private
  artifact" and open the link. The tracker has no publish code.

## Needs you

"Needs you" is one number, the same in Overview, the Lanes For you count, the bottom strip and the Tickets "Needs you" chip (rule: `shared/home-needs-you.js`). The unit is the ticket: the unique tickets with a review card, an open question (every ticket of a grouped question), a reading to confirm, a design pick at the pick stage, or a check to tick on open work. It splits into decisions (questions, readings, picks) and reviews (shipped work, checks), shown as "N to decide, M to review". In Tickets it is a flag on the row, not a state, so a running ticket can carry it and the Running count does not change.

## Tickets view

The Tickets view (key 4, `/dashboard/home/tickets`) is one dense table of every ticket in the project, and the inspector's Tickets tab lists the selected place's open tickets by state. The rules live in `shared/home-ticket-rows.js`.

**States, first match wins:**
- **running**: a session is working on it, waiting on CI, or waiting on you. An idle session is only a quiet "idle" mark.
- **needs you**: an open question or reading to confirm, or a check to tick, by the Plan page's rule (a ticket already in Ready for review stays "in review"). The Needs you chip counts and filters by the flag above, which also covers review cards, picks and running tickets.
- **in review**: in the Ready for review column.
- **ready**: its epic is Ready and the ticket is free to run, by the Plan page's rule.
- **waiting**: in To do or In progress but not free to run; hover the chip to see why.
- **later**: in the inbox or backlog, or under a "later" epic.
- **done**: done or archived; hidden until "show done" is on or the done chip is picked.

Picking a place on the map narrows the table ("Showing Mixer: 23 of 412 tickets. Clear").

**Address parameters** (only differences from the default are written; each project also remembers its own): `tq` text, `tstate` states, `ttype` types, `tgroup` none/place/epic/state/lane, `tsort` and `tdir` sort, `tdone=1` show done, `tlane`, `tmodel`, `tlabel`.

**Keys:** `/` focus the filter box; up/down, PageUp/PageDown, Home/End move the row cursor; Enter opens the ticket; left/right fold a group; `e` selects the row's place on the map; `p` opens its PR; `o` opens its epic; Esc leaves the filter box.

## Adding to the page

Each feature is its own module under `dashboard/js/` that registers itself, plus one import line in
`dashboard/js/home-registry.js`. Nothing else in the shell changes. The API is in
`dashboard/js/home-state.js`:

```js
import { registerHomeView } from './home-state.js';

registerHomeView({
  id: 'map', label: 'Map', key: 2,
  render(root, ctx) { /* build the view into root */ },
  update(root, ctx) { /* optional: refresh in place when tasks change; default re-runs render */ },
  dispose(root) { /* optional: undo timers or listeners */ },
});
```

- `registerInspectorTab({ id, label, render(root, ctx) })`: a tab of the inspector. It is drawn
  again when the selection or the tasks change.
- `registerTopBarItem({ id, slot, render(root, ctx) })`: `slot` is `search`, `palette`, `note` or
  `usage`.
- `registerStripItem({ id, render(root, ctx) })`: an item of the lower strip.
- `registerHomeCommand({ id, title, hint?, keys?, group, run(ctx), when?(ctx), keywords? })`: a palette
  command. `keys` (`"n"`, `"g x"`, `"Mod+J"`) also binds the key and lists it on `?`; a key already taken
  is refused with a console warning. `when(ctx)` hides the command while it does not apply.

Views, top bar items and strip items are drawn again (focus and scroll kept) when the tasks or the
config change. For selection changes, subscribe. `ctx` gives:

| Key | What it is |
| --- | --- |
| `state()` | the tracker's task state (sections, tasks by section, meta) |
| `doc()` | the same as a `tasks.json`-shaped document |
| `selection()` | `{ project, group, area, part }` (ids, `null` when not chosen) |
| `setSelection(where)` | a box id, `{ group, area, part }`, or `null` |
| `clearSelection()` | what `Esc` does |
| `config()` | the project's config as described above (always version 1), or `null` |
| `home()` | the whole `/api/home` answer, errors included |
| `project()` | the selected project slug |
| `openTicket(id)`, `idButton(id)` | open a ticket; a ticket id as a button (same look as the Plan page) |
| `toast(message)` | a short status message |
| `redraw()` | draw this view, tab or item again in place |
| `subscribe(fn)` | `fn({ type })` for `view`, `selection`, `project`, `config`, `tasks`; returns unsubscribe, and ends by itself when the view is left |

A registration with `placeholder: true` gives way to the real one with the same id (for the top bar, any
real item replaces the placeholder of its slot), so a later feature can reserve a zone first.

## Server routes

`GET /api/home?project=<slug>` returns `{ project, projects, path, config, errors, legacy, missing }`.
Routes live in `server/home-routes.js` as a table; each route is its own file under `server/home/`
(`{ method, path, handle }`, returning `{ status?, body }`), added with one line in the table.
`server/home/project-config.js` loads a project's config for any route that needs it, and
`server/home/repos.js` (`resolveRepos(config, configPath)`) turns its `repos` into absolute folders.

`GET /api/home/running?project=<slug>` returns `{ project, at, running[], loose[], epics{}, byTicket{}, warnings[] }`:
the live work of the project (sessions, worktrees, recent commits, pull requests; rules in
`shared/running.js`). One answer is shared for 15 s per project, and a source that cannot be read leaves
its part out with a line in `warnings` instead of failing. `dashboard/js/home-running-data.js` polls it
every 15 s while the Home tab shows (`getRunning`, `onRunning`, `runningFor`, `epicRunState`,
`refreshRunning`); `dashboard/js/home-where.js` tells any view which tickets the selected place keeps
(`selectedEpicIds`, `ticketInSelection`). The "Running now" strip item and its panel are
`dashboard/js/home-running-strip.js`.

`GET /api/home/usage?project=<slug>` returns this week's usage meter; it is cached 60 s, and an older
answer is returned at once (`stale: true`) while a fresh one is read behind it, so only the first read
after a server start waits on the transcripts.

Handbook pages (routes in `server/home/page-routes.js`, spread into the table with one line):
`GET /api/home/page?project=&box=` returns `{ box, name, page, title, updated, covers, markdown, imageBase,
problems, stale, notices }` (or `{ none, expectedPath, template }` / `{ missing: { expectedPath } }`);
`GET /api/home/pages?project=` returns one state row per box (`ok`, `stale`, `missing`, `none`);
`GET /api/home/page-file?project=&path=` serves an image from inside the config's folder, with
`Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` and `nosniff`.
In the page, `pageStateFor(boxId)` (`js/home-pages-data.js`) gives a box's state so the map can draw a book mark.
